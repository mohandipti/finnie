# Deploying Finnie to AWS

I deploy Finnie with AWS CDK (Python). It runs the same Docker image I use locally on a single **EC2 instance** in **us-east-1**. The image lives in **ECR**, the API keys and the MongoDB connection string come from **Secrets Manager** at start-up, and logs go to **CloudWatch**. Accounts and conversations are stored in a free **MongoDB Atlas** cluster outside the AWS account.

```
Allowed IP ─► HTTP :80 ─► EC2 t2.micro (Amazon Linux 2023, default VPC)
                             └─ Docker: Finnie image from ECR (Streamlit :8501)
                                  ├─ API keys and MongoDB URI from Secrets Manager
                                  ├─ logs to CloudWatch (kept 1 month)
                                  └─ MongoDB Atlas M0 (accounts, conversations; allows only the Elastic IP)
```

**Why EC2:** the lab account doesn't support container services (ECS) or load balancers, and only allows `t2.micro` instances in `us-east-1`. A single instance running Docker fits within those limits.

## AWS resources

**Created by the stack** (`cdk deploy`; all removed by `cdk destroy`):

| Resource | Purpose |
|---|---|
| EC2 instance (`t2.micro`, Amazon Linux 2023) | Runs the Finnie container in the default VPC |
| Elastic IP | A fixed public IP that moves to each replacement instance, so the URL and the Atlas allow-list stay the same |
| EBS volume (16 GB gp3, encrypted) | The instance's disk: OS, Docker and the image |
| Security group | Allows inbound HTTP (port 80) only from `allowedCidrs`; all outbound (ECR, Secrets Manager, Gemini API) |
| IAM role + instance profile | Lets the instance pull the image, read the secrets and write logs; plus Systems Manager access for troubleshooting |
| IAM policy | The pull/read/write permissions above, scoped to this image, these secrets and the log group |
| Launch template | Enforces IMDSv2 (token-based instance metadata) |
| CloudWatch log group | Container logs, kept for 1 month |
| Container image in ECR | The Finnie image, pushed by CDK into the bootstrap repository |

**Created once, outside the stack** (kept by `cdk destroy`):

| Resource | Created by | Purpose |
|---|---|---|
| Secrets Manager secret `finnie/google-api-key` | `aws secretsmanager create-secret` | The Google API key (required), read by the instance at start-up |
| Secrets Manager secrets `finnie/alpha-vantage-api-key`, `finnie/serp-api-key` | `aws secretsmanager create-secret` | The Alpha Vantage and SerpAPI keys (optional: without them there are no live prices or news) |
| Secrets Manager secret `finnie/mongodb-uri` | `aws secretsmanager create-secret` | The MongoDB Atlas connection string (optional: without it there are no accounts, and conversations are kept in memory) |
| MongoDB Atlas M0 cluster | The Atlas web console | The database for accounts and conversations; free, hosted by MongoDB on AWS in us-east-1 |
| CDK bootstrap stack `CDKToolkit` | `cdk bootstrap` | An S3 bucket and ECR repository where CDK uploads templates and images, plus its own IAM roles |

**Used but not created:** the account's default VPC and its public subnets.

## One-time setup

1. **Tools:**  AWS CLI configured (`aws configure`), Docker running, and the CDK library installed with `pip install -e ".[infra]"` from the project root. 
2. **API keys:** stored in Secrets Manager, so they never appear in code or CloudFormation. `read -s` waits for me to paste the key's value (not the `NAME=` part) without showing it or saving it in my shell history:
   ```bash
   read -s KEY && aws secretsmanager create-secret --region us-east-1 --name finnie/google-api-key --secret-string "$KEY"; unset KEY
   read -s KEY && aws secretsmanager create-secret --region us-east-1 --name finnie/alpha-vantage-api-key --secret-string "$KEY"; unset KEY
   read -s KEY && aws secretsmanager create-secret --region us-east-1 --name finnie/serp-api-key --secret-string "$KEY"; unset KEY
   ```
   The Google key is required. The other two are optional: if a secret doesn't exist, the app starts without live prices or news. To change a key later, I use `put-secret-value --secret-id <name>` instead of `create-secret --name <name>`. The instance fetches the secrets on every boot, so after changing one I reboot the instance (EC2 → Instance state → Reboot).
3. **MongoDB Atlas:** I created the database by hand once, so deploys never create or replace it:
   1. At mongodb.com/cloud/atlas/register (not AWS Marketplace), create a **Free (M0)** cluster on **AWS, us-east-1**.
   2. **Database Access:** add a user with an autogenerated password and only `readWrite` on the `finnie` database.
   3. **Network Access:** add my laptop's IP for local testing. The instance's Elastic IP is added after the first deploy.
   4. **Connect → Drivers:** copy the `mongodb+srv://` string, put the password in, and store it as plain text (not key/value):
      ```bash
      read -s MONGO_URI && aws secretsmanager create-secret --region us-east-1 --name finnie/mongodb-uri --secret-string "$MONGO_URI"; unset MONGO_URI
      ```
4. **Knowledge base index:** the image includes the FAISS index, so build it first with `finnie-index --rebuild` from the project root.
5. **Bootstrap CDK** once per account and region:
   ```bash
   cd infra
   npx aws-cdk@2 bootstrap aws://<account-id>/us-east-1
   ```

## Deploy

```bash
cd infra
MY_IP=$(curl -s https://checkip.amazonaws.com)
npx aws-cdk@2 diff   -c allowedCidrs=$MY_IP/32     # preview the changes
npx aws-cdk@2 deploy -c allowedCidrs=$MY_IP/32     # build the image, push it, create the instance
```

The app is ready about 5 minutes after the deploy finishes, at the `AppUrl` output: on first boot the instance installs Docker and pulls the image.

After the first deploy, I add the `ElasticIpAddress` output to Atlas **Network Access** as `<ip>/32`, then reboot the instance so the app connects. Until then the app can't reach Atlas, so it runs without accounts and keeps conversations in memory.

I always pass `allowedCidrs` until sign-up exists. Without it the app is open to the internet, and anyone with the URL could use the paid API key. When my IP changes, I deploy again with the new one.

The instance is x86 (`t2.micro`), so the image is built for x86. Docker emulates that on Apple Silicon, which makes the first build take several minutes.

## Updating

After changing code or the knowledge base (rebuilding the index first), I run `deploy` again. A new image **replaces the instance**: the app is down for a few minutes. The Elastic IP moves to the new instance, so the URL and the Atlas allow-list stay the same, and accounts and conversations are kept in Atlas.

## Troubleshooting

- **Logs:** CloudWatch → Log groups → the `LogGroupName` output, or `aws logs tail <LogGroupName> --follow --region us-east-1`.
- **Start-up script:** the first-boot setup is in EC2 → the instance → Actions → Monitor and troubleshoot → Get system log. On every boot, the `finnie` systemd service runs `/opt/finnie/start.sh`, which fetches the secrets and starts the container; `systemctl status finnie` (through Systems Manager Session Manager) shows whether it succeeded.

## Settings

Set in `cdk.json` under `context`, or per command with `-c key=value`:

| Setting | Default | Purpose |
|---|---|---|
| `region` | `us-east-1` | AWS region (the lab account only supports us-east-1) |
| `allowedCidrs` | empty (anyone) | Comma-separated IP ranges allowed to reach the app |
| `secretName` | `finnie/google-api-key` | Secrets Manager secret holding the Google API key |
| `alphaVantageSecretName` | `finnie/alpha-vantage-api-key` | Secrets Manager secret holding the Alpha Vantage key |
| `serpApiSecretName` | `finnie/serp-api-key` | Secrets Manager secret holding the SerpAPI key |
| `mongodbSecretName` | `finnie/mongodb-uri` | Secrets Manager secret holding the MongoDB connection string |
| `instanceType` | `t2.micro` | EC2 instance type (the lab account only supports t2.micro) |

## Removing everything

```bash
npx aws-cdk@2 destroy
```

This removes everything in the stack, including the Elastic IP; a later deploy gets a new one, which I add to Atlas again. The Secrets Manager secrets, the Atlas cluster and the CDK bootstrap resources are separate, so they're kept, and I delete them myself when I no longer need them.

## Design notes

- **CLI credentials.** The lab account doesn't support assuming roles (`sts:AssumeRole` is denied), so the stack uses `CliCredentialsStackSynthesizer`: CDK deploys with the CLI credentials directly instead of the bootstrap roles.
- **Least privilege.** The instance role can only pull the image, read Finnie's secrets and write logs (plus Systems Manager access for troubleshooting). Port 80 is the only inbound port; there is no SSH.
- **Atlas allow-list.** Atlas accepts connections only from listed IPs. The Elastic IP gives the instance one fixed address, so I never need to open Atlas to `0.0.0.0/0`.
- **The keys stay off the console.** The boot script fetches them into a root-only file on every boot and never echoes them.
- **No HTTPS.** HTTPS needs a load balancer, which the lab account doesn't support, or a domain with a certificate on the instance. With an IP allow-list, I accept HTTP for the demo.
- **Headroom.** Finnie uses about 200 MB; the instance has 1 GB of RAM plus 1 GB of swap.
